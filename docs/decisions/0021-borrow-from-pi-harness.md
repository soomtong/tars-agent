# 0021 pi 하네스에서 가져온 것

상태: 확정 (2026-11-15, 사용자가 추천안을 받음). 검토 대상은 pi-mono(badlogic/pi-mono) c3cc916의 agent, codemode, coding-agent, durable 패키지다. 상세는 spec/02, 03, 04, 06, 07.

pi의 codemode는 모델이 쓴 JavaScript를 QuickJS 샌드박스에서 돌리고 바깥에는 도구로만 닿게 한다. 우리 CodeAct와 같은 계열이다. memo(store/load), 능력 사양 예산과 help(describeTool), 끝나지 못하는 대기의 즉시 실패, 잘린 응답의 도구 호출 거부, 프로젝트 설정의 수락, 스킬의 지연 로드는 이미 같은 결론이다. 아래는 우리에게 없거나 달랐던 것이다.

## 결정

명세 보강

1. 크래시 뒤 재개: 세션 파일이 결과 없는 run 줄로 끝나면 재개할 때 crashed 결과를 채워 메시지 짝을 맞춘다. 결과에는 그 run 뒤에 기록된 능력 호출을 적는다. 크래시도 "같은 코드가 연속으로 같은 오류" 규칙에서 센다.
2. 실패한 결과는 그때까지의 출력을 남기고, 이번 스크립트가 부른 능력의 목록과 상태를 붙인다. 실패 전에 일어난 부작용은 되돌리지 않는다는 것을 모델이 알게 한다.
3. 컴팩션 요약의 틀을 정한다: Goal, Constraints, Progress(Done, In Progress, Blocked), Key Decisions, Next Steps, Critical Context, 그리고 호스트가 덧붙이는 목록. 요약 요청에는 대화를 역할 표시가 붙은 텍스트로 풀어 넣고, 사고 블록을 빼고, 결과를 2,000자에서 자른다. 두 번째부터는 이전 요약을 고치게 한다.
4. fs.edit는 정확히 일치하는 곳이 없으면 정규화한 텍스트에서 한 번 더 찾는다. 줄바꿈 형식은 보존한다.
5. MCP 도구는 시스템 프롬프트에 나열하지 않고 help로 찾게 한다.

구조

6. 결과 상한은 모델로 가는 쪽에 건다. 능력이 스크립트에 돌려주는 값은 1 MiB까지 준다.
7. 실행 중에 사용자가 친 입력(steering)을 큐에 두고, 다음 모델 요청 앞에 user 메시지로 하나씩 넣는다. 턴이 끝날 때 큐에 남은 입력은 다음 턴의 입력이 된다.
8. 스텝 벽시계는 VM 안에서 보낸 시간만 잰다. 능력 본체 안의 시간은 승인 대기처럼 빼고, 능력은 자기 시간 제한으로 끝난다.

## 근거

- 6: CodeAct의 이점은 큰 결과를 스크립트 안에서 줄이는 데 있다. 능력 반환값을 30,000자에서 자르면 스크립트가 잘린 값을 가공하게 되어 이점이 깎인다. 모델의 컨텍스트를 지키는 것은 스크립트 결과의 상한이다. 1 MiB는 메모리 상한(256 MiB) 아래에서 충분히 작다.
- 7: 지금은 실행 중에 방향을 바꾸려면 인터럽트로 끊어야 한다. steering은 스크립트를 끊지 않고 다음 스텝에서 지시를 받게 한다. 한 번에 하나씩 넣는 것은 pi의 기본값이고, 모델이 입력마다 응답할 기회를 준다.
- 8: 벽시계(기본 120초)와 proc.exec의 timeout_ms(최대값 제한 없음)가 서로 어떻게 걸리는지 정해져 있지 않았다. 벽시계는 cl_vm_interrupt만 부르므로 능력 안에서 막힌 호출을 끊지 못한다. 능력 안의 시간은 능력의 시간 제한과 취소 플래그가 이미 맡고 있으므로, 벽시계는 스크립트 자신의 계산(무한 루프)만 잡으면 된다.
- 1: 인터럽트는 짝을 맞추는 규칙이 있었지만 크래시는 없었다. 짝이 맞지 않는 히스토리는 제공자가 거부한다. 같은 스크립트로 계속 죽는 경우는 pi의 restartLimit처럼 횟수로 끊는다.
- 5: 서버가 붙고 떨어질 때마다 프롬프트가 바뀌면 캐시가 깨진다.

## 버린 대안

- 스크립트 첫 줄 옵션(`// @options: {"timeout_ms": ...}`)으로 모델이 스크립트마다 시간과 출력 예산을 정하는 것: 8로 시간 문제가 풀리고, 출력 예산은 하네스가 정한다.
- 세션 트리와 분기(/tree, fork): 덧붙이기만 하는 직선 히스토리(ADR 0008)와 맞지 않는다. v1 밖이다.
- 스크립트가 성공했을 때만 store 쓰기를 남기는 것: memo는 panic과 인터럽트에도 남는 것이 존재 이유다.
- 한 호출에 여러 편집(edits[]): 스크립트가 fs.edit를 여러 번 부르면 된다.
- 파일별 변경 큐: v1은 spawn을 막아 능력이 한 스레드에서만 불린다.
- 결정적 리플레이를 위한 seed와 시작 시각 주입: 지금은 하지 않는다. 시계는 time 모듈이 직접 읽어 기록에 남지 않는다. 필요해지면 ADR 0024의 "다시 볼 때"로 간다.
- follow-up 큐(턴이 끝난 뒤에 처리할 입력)를 따로 두는 것: 턴이 끝날 때 남은 steering 입력이 그 역할을 한다. 큐가 둘이면 사용자가 입력마다 어느 쪽인지 골라야 한다.

## 열어 둔 것

- 컴팩션에서 최근 구간(pi는 약 20k토큰)을 원문으로 남기는 것. 자르는 위치는 user 메시지 경계다. 직전 작업의 맥락이 요약에서 덜 빠진다. 앞부분이 바뀐 대화에 남긴 assistant 블록의 사고 블록을 API가 받는지 확인하지 않았다. 이것은 ADR 0008의 근거와 닿는다. 확인한 뒤 정한다 (TODO M4).
