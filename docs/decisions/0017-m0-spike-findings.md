# 0017 M0 스파이크의 발견과 본체에 대한 추천

상태: 발견은 확정 (2026-11-13, 실측). 추천은 확정이 아니다. 본체를 만들 때 단계마다 사용자가 정한다 (ADR 0012의 덧붙임).

상세: docs/spikes/2026-11-13-m0-spikes-review.md. cyber 요청: docs/requests/cyber-m0-spike-findings.md.

## 증명된 것

- Zig 0.17.1 호스트가 libcyber 0.4.9를 정적 링크해 VM을 돌린다. 검사 31개가 macOS arm64와 tars 게스트(x86_64-linux-gnu)에서 통과했다.
- 승인 대기를 VM 밖에서 하는 설계(0011, 0016)가 고칠 것 없이 돈다: 승인, 거부, 취소, 버린 요청, 동시 요청, 중첩 scope.
- 상한 넷이 폭주를 멈추고 VM은 계속 쓸 수 있다.
- Zig std.http로 스트리밍 요청이 된다. TLS와 CA 묶음은 macOS와 tars 게스트 모두에서 됐다. curl 대안은 필요 없다.
- 0015의 방향이 맞다. 블록 넷과 thinking의 불투명 칸 하나로 두 형식, 제공자 둘, 모델 셋을 받았다.
- 에이전트 루프 전체(direct, CodeAct)가 tars 게스트 안에서 돌았다.

## 깨진 것

- cyber: 실패한 컴파일 뒤 다음 컴파일에서 프로세스가 죽는 경로가 있다. 첫 CodeAct 세션에서 났다.
- cyber: `!str` 값을 복사하지 못해 `Future[!str]`을 쓸 수 없다.
- cyber: 의존으로 받아도 라이브러리 아티팩트가 나오지 않는다.
- 작은 모델(qwen3.8-flash)은 CodeAct에서 과제당 6~10번 컴파일에 실패했고 과제 셋 중 하나를 못 끝냈다. deepseek-chat과 qwen3.8-max는 셋 다 끝냈다.

## 스파이크 안에서 Claude가 정한 것 (위임받은 결정)

- 순서: 스파이크 1, 2a, 2b, 3. 사용자에게 추천한 순서(2a 먼저)와 다르게 위험이 큰 호스트 경계부터 했다.
- cyber.h는 translate-c 패키지로 가져왔다. 본체의 추천은 손으로 쓴 extern이다.
- 문자열 결과는 손잡이로, 검증은 fork한 자식에서.
- 모델이 쓴 명령은 샌드박스에서만 돌렸다(macOS sandbox-exec: 쓰기는 작업 폴더, 네트워크 차단, 사용자 폴더 읽기 차단, 명령당 20초).
- 스파이크 코드는 spike/에 커밋해 두었다. 검토가 끝나면 지운다.

## 본체에 대한 추천

검토 문서 8절의 열다섯 항목이다. 구조에 닿는 것만 여기 옮긴다.

1. 명세 01의 구성요소와 경계는 그대로 간다.
2. 능력은 모두 `Future[!T]`를 돌려주고 머리말 래퍼가 await한다. 승인이 필요 없으면 호스트 함수 안에서 바로 완료한다.
3. 호스트 로더는 허용 목록이다. 능력 함수는 메인 스레드가 아니면 panic을 돌려준다.
4. 프로세스 실행 능력은 자체 시간 상한, 표준 입력 차단, 출력 상한, 취소를 가진다. VM의 타이머는 승인 뒤 루프가 돌리는 프로세스에 닿지 않는다.
5. 읽기 능력도 권한의 대상이다. 읽은 것은 모두 모델 제공자에게 간다.
6. 실패한 컴파일로 죽는 결함이 고쳐지기 전에는 검증을 자식 프로세스에서 한다. 0009의 "실행 프로세스 분리"를 되살리는 조건에 해당하는지 본체에서 다시 본다.
7. direct 모드는 대조군이면서 작은 모델용 기본값 후보다.
