# 0016 동시 승인은 하나씩 묻고, v1 안내는 fiber와 scope를 가르치지 않는다

상태: 확정 (2026-11-12). Claude의 추천안을 사용자가 받았다. 0011의 "v1은 동시 실행을 보이지 않는다"를 cyber의 fiber 동작에 맞춰 구체화한다.

## 배경

cyber에서 fiber 안의 await는 그 fiber만 멈춘다. eval이 CL_AWAIT로 나가는 것은 루트가 기다릴 때(루트의 await, Future.wait_any, Fiber.wait_ready(), scope 블록의 합류)뿐이다. 그래서 다음 셋이 생긴다 (spec/08의 fiber와 scope 항목).

- 스크립트가 능력 호출을 fiber나 scope 블록에 넣으면 한 번의 CL_AWAIT에 승인 요청이 여럿 걸린다. cl_vm_pending_futures가 순서 없이 전부 준다.
- fiber를 직접 resume하는 루프가 Fiber.wait_ready()를 부르지 않으면 호스트가 승인할 기회 없이 연료, 시간 상한까지 돈다.
- scope 블록의 fiber 하나가 오류(error.Denied 포함)를 돌려주면 나머지 fiber는 취소되고, 그들이 기다리던 요청은 알림 없이 버려진다.

## 결정

1. 동시 승인은 하나씩 묻는다. CL_AWAIT로 돌아오면 루프는 cl_vm_pending_futures의 목록에서 우리 요청(태그가 0이 아닌 것) 가운데 요청 번호가 가장 작은 것 하나를 골라 승인을 받고, 완료한 뒤 cl_vm_resume한다. 남은 요청은 다음 CL_AWAIT로 다시 온다. resume 뒤에는 목록을 다시 읽는다. 목록에 우리 요청이 하나도 없으면(모두 태그 0) 0011대로 abandon한다.
2. v1의 프롬프트 안내는 fiber와 scope 블록을 가르치지 않는다. 능력 호출을 fiber나 scope 블록에 넣지 않는다는 한 줄을 둔다. 막는 장치는 넣지 않는다: 모델이 그래도 쓰면 1번의 경로로 맞게 처리된다.
3. 거부로 취소된 요청을 닫는 장치는 따로 두지 않는다. 1번에서 화면에 올라간 요청은 항상 하나이고 그것은 답을 받은 것이다. 묻지 않은 채 버려진 요청은 eval이 끝날 때(CL_SUCCESS, panic, interrupt, abandon) 요청 표를 비우는 기존 규칙(spec/08)으로 사라진다.

## 근거

- 루프의 모양이 요청 하나짜리 설계와 같다. "CL_AWAIT, 승인 하나, 완료, resume"을 되풀이하면 요청이 하나든 여럿이든 같은 코드가 처리한다. 승인 화면과 코어-프런트엔드 이벤트 타입도 요청 하나짜리로 남는다.
- 번호 순으로 고르면 실행이 재현된다. cyber의 목록은 순서가 없어서 호스트가 정하지 않으면 묻는 순서가 실행마다 달라질 수 있다. 요청 번호는 능력이 불린 순서다.
- 안내에서 가르치지 않아도 안전에는 영향이 없다. 실제 작업은 승인 뒤 호스트가 하므로 기다리지 않고 버려진 요청은 아무 일도 하지 않는다 (spec/05).
- scope를 가르치는 이득(읽기 여러 개를 동시에)이 아직 측정되지 않았다. 능력의 대부분은 승인 없이 바로 완료된 Future를 돌려주므로 fiber에 넣어도 빨라지지 않는다. 이득은 호스트가 능력을 실제로 병렬 실행할 때 생기고, 그것은 0009의 spawn 행과 0011이 평가 뒤로 미룬 일이다.
- 가르치면 모델이 틀릴 자리가 늘어난다: out.* += fut.await()의 덮어쓰기, suspend만 도는 fiber와 섞일 때의 연료 소진, 빌림 인자 규칙.

## 버린 대안

| 대안 | 버린 이유 |
|---|---|
| 요청을 한 화면에 모아 묻기 | 승인 화면과 이벤트 타입이 요청 묶음을 다뤄야 한다. 일부만 승인했을 때의 표시와 기억 규칙이 더 생긴다. 완료한 fiber가 다음 요청을 내면 목록이 바뀌어 묶음이 한 번에 끝나지도 않는다 |
| scope 블록만 가르치기 (cyber의 추천) | 기다리지 않는 루프가 구조적으로 생기지 않는 장점은 맞다. 다만 v1에서 동시 실행을 보이지 않는다는 0011과 어긋나고, 이득이 측정되기 전에 안내가 길어진다. 되살리는 조건에 둔다 |
| fiber와 scope를 호스트가 막기 (소스 검사나 로더) | cyber에 그런 임베딩 옵션이 없고, 막지 않아도 1번으로 맞게 돈다 |

## 되살리는 조건

- 평가에서 모델이 안내 없이도 fiber나 scope를 자주 쓰거나, 그 때문에 연료 상한에 닿는 실패가 반복되면: scope 블록만 가르치는 쪽으로 2번을 다시 본다.
- 호스트 쪽 병렬 능력을 넣기로 하면(0009의 spawn 행): scope 블록이 그 문법이 되므로 2번과 "모아 묻기"를 함께 다시 본다.

## 바뀌는 것

- spec/02의 실행 단계: 요청이 여럿이면 번호가 가장 작은 것부터 하나씩.
- 프롬프트 안내(한/영): 능력 호출을 fiber나 scope 블록에 넣지 않는다는 한 줄.
- M0 스파이크 1이 확인했다: 요청 둘을 scope 블록으로 걸면 번호 순으로 하나씩 완료되고, 중첩 블록도 끝까지 가고, 하나를 거부하면 나머지는 묻지 않은 채 버려지고 요청 표는 eval 끝에 빈다 (ADR 0017).
