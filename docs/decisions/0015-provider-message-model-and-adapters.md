# 0015 제공자: 자체 메시지 모델과 형식별 어댑터

상태: 방향 확정 (2026-11-12, 사용자 동의). 타입의 세부는 M0 스파이크 2a 뒤에 정한다.

## 결정

- tars-agent는 자체 메시지 모델을 가진다. 코어(loop, session, 프런트엔드)는 이 모델만 본다.
- 전송 형식마다 어댑터를 둔다. 지금은 둘이다: Anthropic Messages, OpenAI Chat Completions (ADR 0014).
- 형식과 제공자는 다른 축이다. 형식은 코드(어댑터)이고, 제공자는 데이터다: 기준 주소, 인증 헤더, 모델 이름, 쓰는 형식. DeepSeek은 한 제공자가 두 형식을 다 말한다. 새 제공자는 대부분 설정 한 항목이고, 어댑터는 형식이 새로 생길 때만 는다.

## 이유

- 사용자: 지금은 형식이 둘이지만 제3의 것이 생길 수 있다. 어댑터로 여럿에 대응하거나 자체 메시지 모델을 세운다.
- 둘은 한 설계의 두 면이다. 어댑터가 맞춰 줄 대상이 자체 메시지 모델이다.

## 방향 (세부는 2a 뒤에 확정)

- 메시지 모델은 블록 기반이다. 메시지 하나가 블록의 목록이고 블록은 text, thinking, tool_call, tool_result다. Anthropic 형식이 이 모양이고 OpenAI 형식은 이 모양으로 옮길 수 있다. 반대 방향은 정보가 빠진다.
- 스트리밍은 내부 이벤트 하나로 맞춘다: 글자 조각, 사고 조각, 도구 호출 시작, 인자 조각, 끝, 사용량.
- 끝난 이유는 필드를 옮겨 적지 않고 내용에서 다시 계산한다. tool_use 블록이 있는데 stop_reason이 end_turn으로 온 사례가 있다 (ADR 0014).
- 어댑터 인터페이스는 작게 둘이다: 요청 만들기(내부 히스토리, 도구, 옵션 -> 요청 본문)와 스트림 풀기(SSE -> 내부 이벤트).
- "받은 그대로"(명세 02): 블록마다 불투명한 원문 칸을 둔다. 출처 형식과 원문 바이트가 들어가고 그 형식의 어댑터만 해석한다. 코어는 건드리지 않고 실어 나른다. 세션 중간에 형식이 바뀌면 다른 형식의 원문은 버린다. 글과 도구 호출은 남고 사고는 빠진다.
- 한쪽 형식에만 있는 기능(캐시 지점, effort)은 힌트 옵션이다. 지원하는 어댑터는 쓰고 못 하는 어댑터는 무시한다.
- 제3의 형식은 미리 만들지 않는다. 어댑터 둘로 만들고 인터페이스가 둘의 사정에 묶이지 않았는지만 확인한다. 후보는 OpenAI Responses API와 Gemini다.

## 2a 뒤에 정할 것

- 블록 넷으로 충분한지, 불투명 칸이 정말 필요한지 (두 형식의 실제 응답으로 확인)
- 사고의 보관과 되돌리기: Anthropic의 서명 있는 thinking 블록, DeepSeek과 Qwen의 reasoning_content
- 어댑터를 Zig에서 어떻게 표현할지 (tagged union, vtable, comptime)
- 제공자 설정의 자리와 형식

## 바뀌는 것

- 페어 4번(ADR 0012)은 "메시지 모델과 어댑터 인터페이스"로 커진다. 구조 코드라 사용자가 직접 편집할 후보다.
- 명세 01의 경계 규칙 "provider는 제공자 차이를 흡수한다"가 이 결정으로 구체화된다. 명세 02의 모델 요청 절은 2a 뒤에 고친다.
