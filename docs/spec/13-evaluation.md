# 평가 (eval/)

평가는 모델이 Cyber로 일하는 정확도를 재고 CodeAct를 기본으로 둘지 판정하는 도구다 (ADR 0006, 01 "핵심 설계 선택 1"). 스파이크와 달리 eval/은 남긴다. 평가는 본체의 헤드리스와 direct 모드가 선 뒤(M2 뒤)에 돈다(TODO E). 요구는 12 문서의 R-EVAL 줄이다. 아래 결정은 ADR 0031에서 정했다.

## 쓰임

- 판정: CodeAct 대 direct (ADR 0006 결정 3).
- 안내 고치기: Cyber 안내의 문구는 평가의 실패 유형에서만 고친다 (06).
- cyber에 만들 것의 증거: 실패 유형이 08 "cyber에서 만들 것"의 근거가 된다 (ADR 0010).
- 기준 빌드를 올릴 때 다시 돌린다 (TODO C의 마지막 줄).
- 시험할 선택: 검증의 오류 모아 받기(cl_vm_set_error_recovery, 검토 문서 9절 13), 쓰지 않는 지역 넘기기(cl_vm_symbol_hints, 9절 18), 03의 생략할 수 있는 인자의 모양.

## 비교하는 것

- CodeAct: run 도구 하나, 능력은 Cyber 함수.
- direct: 같은 능력 표를 API 도구 여럿으로 노출하고 VM을 쓰지 않는다 (01, ADR 0006 결정 2).
- 두 모드는 능력, 권한, 세션, 프런트엔드를 같이 쓴다. 다른 것은 모델에게 보이는 표면과 시스템 프롬프트뿐이다.
- 모드와 제공자를 고르는 명령행 인자는 11이 정한다. json에서 direct의 도구 호출 하나는 능력 호출 하나짜리 run이고 validate가 없다(06).

## 스파이크의 비교 회차에서 쓴 방법 (사실)

출처: 검토 문서 5절, 5.3, spike/s2/compare.sh. 과제 셋, 판정이 아니라 감을 잡기 위한 것이다.

- 과제 하나는 셋이다: 작업 폴더를 만드는 fixture(고정 시드의 파이썬 스크립트가 로그, 소스, 설정 파일을 쓴다), 영어 프롬프트 한 문단, 검사 함수.
- 과제마다 fixture를 새로 만들고 s2를 헤드리스로 한 번 돌린다. 승인은 자동이고 모델이 쓴 명령은 샌드박스(spike/s2/src/jail.zig, macOS sandbox-exec: 쓰기는 작업 폴더, 네트워크 차단, 명령당 20초) 안에서만 돈다.
- 채점은 실행 뒤 작업 폴더의 파일을 본다. 모델의 답 글은 보지 않는다. T1, T2는 출력 파일을 기대 문자열과 바이트로 비교하고(T1은 공백을 지운 뒤), T3는 configparser로 값 넷을 본다. 결과는 PASS 또는 FAIL이다.
- 컴파일 오류 수는 실행 추적(stderr)에서 센다.
- 한 줄 기록의 열: 과제, 판정, 제공자, 모델, 모드, 스텝, 도구 호출, 도구 오류, 입력 토큰, 캐시된 입력, 출력 토큰, 밀리초, 컴파일 오류.
- 표로 모은 값: 통과 수, 스텝 평균, 과제당 컴파일 오류, 오류가 난 과제 수, 과제당 시간, 과제당 입력 토큰(캐시 몫 포함)과 출력 토큰(사고 포함), 캐시가 덮은 몫.
- 사람이 읽고 나눈 것: 실패의 원인(과제 해석, 모델의 판정 실수, cyber 결함), 컴파일 오류의 첫 줄과 "문구가 고치는 법을 말하는가"(5.1), run 스크립트의 꼴(셸 위임, 입출력만, 로직, 5.2).
- 회차 운영: 회차 전에 안내를 확정하고 회차 도중에 고치지 않는다. 회차는 같은 작업 폴더를 쓰므로 차례로 돌린다. 원자료는 기준 빌드 이름의 폴더에 둔다.
- 배운 것: 프롬프트의 문장은 뜻이 하나여야 한다. 두 회차에서 실패 둘이 과제 해석("file names without the folder", 경로를 붙여 씀)이었다.

## 과제

과제가 갖출 것

- fixture: 같은 입력을 매번 만든다(고정 시드). 작업 폴더 밖에 쓰지 않는다.
- 프롬프트: 영어, 뜻이 하나인 문장. 출력 형식(파일 이름, 줄 꼴, 정렬)을 글자 그대로 적는다.
- 검사: 실행 뒤 작업 폴더의 상태로 판정하는 스크립트. 답 글로 판정해야 하는 과제는 기대 값이 글에 정확히 나오는지만 본다.
- 범주 표시: 아래 고르는 기준의 어느 것인지.

고르는 기준

- 실제 쓰임에서 고른다: 파일 찾아 고치기, 여러 파일 집계, 명령 실행 후 출력 가공, 오류 처리, JSON 꺼내기.
- JSON을 다루는 과제를 넣는다. 08의 C1 근거가 "평가 과제의 다수가 JSON을 다룬다"이다. 평가는 json 모듈을 안내에 넣은 뒤 돌린다 (TODO E).
- 열린 표준 모듈(regex, time, path)을 써야 자연스러운 과제를 넣는다. 0.4.15 회차에서 연 모듈은 한 번도 쓰이지 않았다(검토 5.3).
- 한 스텝에 여러 능력 호출과 가공이 드는 과제(CodeAct의 이점)와 한두 번의 읽기로 끝나는 과제(direct가 유리할 자리)를 함께 둔다.
- 평가는 승인 없이 돈다(아래 "실행 환경"). 승인과 거부의 경로는 M2 게이트와 테스트가 본다. 네트워크가 필요한 과제(net.fetch)는 두지 않는다.

수: 20개. 회차: 과제마다 3회, (모델, 모드) 조합마다 (ADR 0006).

과제 파일의 모양

- 과제마다 eval/tasks/<이름>/ 디렉터리 하나에 prompt(영어 한 문단), fixture, check를 둔다. 범주 표시는 prompt 옆의 짧은 메타 파일에 둔다.
- fixture와 check는 파이썬 표준 라이브러리만 쓴다. 스파이크의 방법과 같다.
- 첫 과제 둘을 만든 뒤 사용자에게 보이고 모양을 확정한다. eval/은 Claude가 채우는 기능 쪽이지만 오래 남는 도구다.

## 실행 환경

- 평가는 본체의 헤드리스(-p, json 출력) 위에서 돈다. 스파이크 s2를 고쳐 쓰지 않는다. 판정은 본체가 쓸 하네스로 해야 뜻이 있고, 결과가 바꾸는 것은 기본 모드뿐이라 M1~M2를 먼저 만들어도 버릴 것이 적다.
- 권한: 바깥 OS 샌드박스 안에서 bypass 모드로 돌린다. 평가 실행기가 하네스를 샌드박스(macOS sandbox-exec, 스파이크 jail과 같은 규칙) 안에서 시작한다. 쓰기는 과제의 작업 폴더와 세션 디렉터리만이다. 하네스는 제공자에 닿아야 하므로 네트워크는 제공자 연결에 필요한 만큼 연다. 근거: 평가가 재는 것은 모델의 정확도이고 권한 거부가 섞이면 실패 원인이 흐려진다.

## 채점과 기록

판정은 검사 스크립트가 한다. 회차마다 헤드리스 json 결과(06, ADR 0030 결정 4)와 세션 파일(07)을 함께 남긴다.

헤드리스 json에서 읽는 필드

| 기록 항목 | 읽는 곳 |
|---|---|
| 과제 성공 | 검사 스크립트. json이 아니다 |
| 사람이 끊은 회차 | exit_code 130. 실패로 세지 않고 다시 돌린다 (ADR 0030 근거 4) |
| 멈춘 이유 | stop, exit_code (max_steps, budget, repeated_error는 실패로 센다) |
| 스텝 수 | steps |
| run 수, run마다 검증 결과 | runs[].validate (ok, compile_error) |
| 실패 종류 | runs[].outcome (02의 일곱 종류) |
| 능력 호출과 결정, 오류 이름 | runs[].caps[].name, decision, error |
| 실행 시간 | runs[].ms의 합 (스크립트 실행만이다. 모델 대기는 들지 않는다) |
| 전체 걸린 시간 | ms (모델 대기 포함, 06) |
| 토큰 | usage.input, output, cache_write, cache_read |
| 비용 | cost_usd |
| 제공자 | provider (06) |
| 모델 | model |
| 하네스 오류 | error.kind, error.message |

세션 파일에서 읽는 것

- 컴파일 오류의 문구와 위치: run 줄의 validate 결과(02 절차 3의 구조화한 필드). json에는 문구가 없다.
- 스크립트 본문: run 줄의 코드. 스크립트의 꼴(5.2)을 나눌 때 쓴다.

회차에 함께 적는 조건

- cyber 버전 문자열, 안내의 판(바이트 수), 시스템 프롬프트 바이트 수.
- 제공자, 날짜가 붙은 모델 ID (ADR 0014), effort와 사고 설정. 제공자와 모델은 json에도 있다.
- 권한 모드와 샌드박스.

모으는 값 (TODO E의 기록 항목에 스파이크의 표를 더한 것)

- 첫 시도 validate 통과율(CodeAct만. 셈은 아래 "판정"), run마다의 검증 통과율, 첫 run이 검증을 통과한 과제의 비율, 과제 성공률, 스텝 수, 토큰(입력, 그중 캐시, 출력), 실패 유형.
- 과제당 컴파일 오류, 오류가 난 과제 수, 과제당 시간, 캐시가 덮은 몫.
- 죽은 실행(crashed), 상한에 걸린 실행(interrupted), panic, 세션 reset의 수.
- 실패 유형은 실패 종류(outcome)와 사람이 나눈 원인(과제 해석, 모델 판정 실수, Cyber 문법, 능력 사용, cyber 결함)이다. 컴파일 오류는 첫 줄과 "문구가 고치는 법을 말하는가"로 나눈다(5.1). 고치는 법을 말하지 않는 문구가 회차에서 되풀이되면 cyber에 요청서를 낸다.

## 모델

- 판정 모델은 개발 기본 제공자의 모델 DeepSeek-V4.1-Flash다 (ADR 0014). 키가 있고 개발 기본이다. ANTHROPIC_API_KEY는 없다.
- 같은 표에 OpenRouter의 Qwen 둘을 함께 기록한다. 판정 모델과 합쳐 크기가 다른 모델 셋이다(검토 9절 16). 스파이크 회차에서 과제당 컴파일 오류가 모델에 따라 0에서 2.20까지 달랐다(검토 5.3).
- 모델 사이의 차이가 판정을 가르면 모델마다 판정하고 기본 모드를 모델 설정의 값으로 둔다.
- 평가를 시작하는 날 OpenRouter 목록을 다시 보고 날짜가 붙은 ID로 고정한다(ADR 0014). Qwen4가 있으면 그것으로 한다.
- 사고 설정은 모델마다 기본값 하나다. DeepSeek의 사고 있음과 없음은 회차 차이가 보이지 않았으므로(검토 5절) 하나만 둔다.

## 판정 (ADR 0006)

판정 모델에서

- 첫 시도 validate 통과율 70% 이상
- 과제 성공률이 direct보다 5%p 넘게 낮지 않음

둘 다 넘으면 CodeAct가 기본이다. 못 미치면 안내를 실패 유형에 맞춰 고치고 한 번 더 잰다. 그래도 못 미치면 direct를 기본으로 하고 CodeAct는 선택 모드로 둔다. 평가 표와 판정은 docs/decisions에 남긴다 (TODO E 게이트).

첫 시도 validate 통과율

- 분자와 분모는 모델이 새로 쓴 스크립트다. 직전 run이 compile_error가 아닌 run만 센다. 오류 문구를 보고 고친 스크립트는 첫 시도가 아니다. 분모는 그런 run의 수, 분자는 그 가운데 검증이 ok인 run의 수다.
- 근거: "첫 시도"는 오류 문구를 보기 전에 쓴 코드의 정확도다. run마다 세면 고치는 run이 섞여 오류가 많을수록 분모가 커진다.
- run마다의 통과율(검증 ok인 run / 모든 run)과 과제마다의 통과율(첫 run이 검증을 통과한 과제 / 과제)도 함께 적는다. 판정에는 쓰지 않는다.
