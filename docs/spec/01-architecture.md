# 아키텍처

## 프로세스 모델 (ADR 0004)

세션 하나에 프로세스 하나다. tars-agent 실행 파일이 코어를 링크하고 프런트엔드(대화형 또는 헤드리스)를 하나 고른다. 데몬은 없다.

- 스레드: 메인 스레드가 루프와 VM을 돈다. 보조 스레드는 둘이다. 입력 스레드(키 입력, 인터럽트)와 타이머 스레드다. 타이머 스레드는 벽시계(wall-clock) 상한에서 cl_vm_interrupt를 부른다.
- 승인 대기는 VM 밖, 루프의 바닥에서 한다 (ADR 0011). 승인이 필요한 능력은 미완료 Future를 돌려주고, eval이 CL_AWAIT로 돌아오면 루프가 승인을 받고 resume한다. 세션이 하나이므로 "다른 세션이 막히지 않는다"는 불변식은 프로세스 격리로 성립한다.
- 여러 세션이 필요하면 패널마다 tars-agent를 하나씩 띄운다. VM 하나가 쥔 메모리는 약 2.6 MiB다(08). 하네스 프로세스 전체의 메모리는 재지 않았다(아래 열린 것 4).
- 데몬(agentd)이 필요해지는 때는 tars 터미널 제어 채널이나 MCP 서버 방향을 만들 때다. 그때 데몬은 헤드리스 stream-json 프로토콜을 말하는 프런트엔드 하나로 얹는다 (06).

## 구성요소

~~~text
frontend    repl (대화형) / headless (-p, text | json | stream-json)
   |        이벤트 스트림 (코어 -> 프런트엔드), 명령 (프런트엔드 -> 코어)
core
   +-- session      히스토리, 기록(JSONL), 재개, 컴팩션
   +-- loop         모델 호출 - 검증 - 실행 반복 (02)
   +-- provider     자체 메시지 모델, 형식별 어댑터 둘(Anthropic Messages, OpenAI Chat Completions), 제공자 설정, SSE 스트리밍, 재시도 (10)
   +-- prompt       시스템 프롬프트 조립: 규칙, Cyber 안내, 능력 사양, 환경, AGENTS.md
   +-- runtime      libcyber VM: 로더, validate, eval, 연료(fuel), 스택/메모리 상한, 중단
   +-- caps         능력 표 (단일 소스) 와 본체 (03, 04)
   +-- permission   프로파일, 모드, 규칙, 승인 요청 (05)
   +-- sandbox      실행 프로세스의 Landlock 제한 (Linux)
~~~

## 핵심 설계 선택 1: CodeAct

- API 수준의 도구는 run 하나다. 읽기, 검색, 편집, 실행은 모두 Cyber 안에서 능력 함수로 부른다.
- 장점: 한 스텝에 여러 호출과 분기, 반복, 중간값 가공을 모델 왕복 없이 처리한다. 큰 결과를 모델에 보내지 않고 스크립트 안에서 줄인다. 도구 정의 토큰이 도구 수에 비례하지 않는다.
- 단점: 모델이 Cyber를 써야 한다. 학습 데이터가 적고 정적 타입과 소유권이 있어 틀리기 쉽다. 대응은 복사 가능한 타입(int, str, []T)만 쓰는 부분집합을 가르치고, eval 전에 cl_vm_validate로 검증해 오류를 되돌리는 것이다.
- 이 단점은 프로젝트의 가장 큰 위험이라 측정으로 판정한다. M0의 평가에서 기준(TODO M0)을 넘지 못하면 기본 모드를 direct로 바꾼다.

## 핵심 설계 선택 2: 능력 표 단일 소스 (ADR 0006)

능력은 Zig comptime 표 하나에 정의한다. 항목은 이름, 매개변수 타입, 반환 타입, 등급, 사양 문서, 본체 함수다. 이 표에서 넷을 만든다.

- Cyber 선언 (#[bind] fn) 과 cl_mod_add_func 바인딩
- 시스템 프롬프트의 능력 사양
- JSON Schema: direct 모드의 API 도구 정의, 후속의 MCP 서버 방향
- 권한 게이트의 등급 표

본체는 VM을 모른다. 인자를 Zig 값으로 받고 Zig 값이나 오류를 돌려준다. Cyber 값 변환과 소유권 해제(cl_str_deinit 등)는 생성된 바인딩 층 한 곳에서만 한다. 능력을 하나 더하는 일이 표에 한 항목을 더하는 일이 된다.

direct 모드는 같은 표를 API 도구 여럿으로 노출하고 VM을 쓰지 않는다. 평가의 대조군이고, CodeAct가 기준에 못 미칠 때의 기본값이다.

## 경계 규칙

- 스크립트는 능력으로만 세계에 닿는다. 로더는 os 모듈을 모르고, 호스트 로더는 허용 목록이며, c 모듈은 deny_raw_ptrs와 -Dffi=false로 무력하다 (05, ADR 0026).
- 프런트엔드는 입출력과 승인 화면만 그린다. 정책 판단은 코어에 둔다. 코어는 터미널을 직접 만지지 않고 이벤트를 낸다.
- provider는 제공자 차이를 흡수한다. 코어는 자체 메시지 모델만 본다. 형식마다 어댑터가 있고, 제공자는 설정 데이터다 (ADR 0015, 10). assistant 블록은 받은 그대로 보관하고(02), 형식마다 다른 원문은 블록의 불투명 칸에 실어 같은 형식 안에서 그대로 되돌린다.
- libcyber는 runtime 모듈 밖으로 새지 않는다. cl_* C ABI를 runtime/cy.zig 한 파일이 감싼다. fork에 Zig 전용 표면을 만들지 않는다.
- Cyber 컴파일러와 VM에 남은 abort와 세그폴트 경로는 fork의 버그로 다룬다 (ADR 0010, 0019). 스크립트가 VM을 죽여 프로세스가 끝나는 경우를 전제로 둔다 (ADR 0017 추천 10). 실행 프로세스 분리는 죽는 비율을 재 본 뒤 판단한다 (ADR 0009, 아래 열린 것 1).

### 프로세스가 죽을 때의 대응

- 기록: run 줄을 실행 전에 쓰므로 무엇을 하다 죽었는지 남는다 (02 기록 순서, 07 쓰기와 복구). write가 끝난 줄은 kill -9에도 남는다.
- 재개: --continue로 이으면 결과 없는 run 줄에 crashed 결과를 채워 메시지 짝을 맞추고, 그 run 뒤의 cap 줄(이미 효과가 났을 수 있는 호출)을 결과에 적는다. 스크립트는 다시 실행하지 않는다. 그 스크립트를 세션 디렉터리의 crash/에 보관하고 사용자에게 알린다 (02 세션 재개, ADR 0021 결정 1).
- 반복: crashed도 같은 오류로 센다. 같은 코드가 5회 연속 죽으면 턴을 끝낸다 (02 한도).
- 재현: crash/의 스크립트는 cyber에 낼 재현 사례다 (08 "cyber에서 만들 것"의 수시 줄).
- 빈 곳: run 줄은 검증 결과를 담으므로 검증 뒤에 쓴다 (07). 검증 중에 죽으면 run 줄이 없고 코드는 assistant 줄의 tool_call에만 남는다. 02의 재개 규칙은 결과 없는 run 줄만 본다. 처리는 02 열린 것 3.

### 죽는 비율을 재는 법

- 단위는 모델이 낸 run 호출(tool_call) 하나다. 죽은 run은 결과 없이 프로세스가 끝난 run이다. 검증 중(run 줄 없음)과 실행 중(run 줄 있음)을 나눠 센다.
- 분모는 run 호출 수, 분자는 죽은 run 수다. 세션 파일에서는 결과 없는 run 줄로 끝난 세션, 재개가 채운 crashed 결과 줄, 위 빈 곳의 run 줄 없는 tool_call을 센다. 같은 tool_use_id는 한 번만 센다. 세션 줄의 cyber 버전(07)으로 판마다 나눈다.
- 첫 측정은 E 평가 회차다. 프로세스가 죽으면 헤드리스 json 결과가 나오지 않으므로 json의 runs[].outcome으로는 셀 수 없다. 평가 실행기가 신호로 끝난 회차를 죽은 회차로 세고, 그 회차의 세션 파일에서 죽은 run을 찾는다.
- M4부터는 사용 중의 세션 파일로 같은 셈을 한다 (tars-agent stats, 07). 재개하지 않은 세션의 결과 없는 run 줄도 죽은 run으로 센다.
- 지금 아는 값: 0.4.15 비교 회차에서 run 206개 가운데 죽은 run은 0개다 (검토 문서 5.3).

## 저장소와 배포 (ADR 0005)

- 코드는 이 저장소(tars-agent)에 둔다. cyber는 build.zig.zon의 의존으로 태그와 해시를 고정해 소스에서 빌드하고 정적 링크한다 (-Dffi=false). libcyber를 따로 배포하지 않는다.
- 산출물은 x86_64-linux-gnu 동적 링크(glibc) 실행 파일 하나다. GitHub 릴리스에 올리고 tars-linux가 devlayer/manifest.toml에 url과 sha256으로 들인다. cyber, cci와 같은 길이다.
- 개발용으로 aarch64-macos 빌드도 유지한다.

## 열린 것

구조에 닿으므로 사용자가 정한다 (ADR 0012). 추천은 Claude의 것이다.

1. 실행을 별도 프로세스로 뗄지 (ADR 0009, 0017 추천 10)
   - 선택지: (a) 지금대로 한 프로세스. 죽으면 사용자가 --continue로 잇는다. (b) 감시 프로세스: tars-agent가 자기를 자식으로 띄우고, 자식이 신호로 끝나면 같은 세션을 --continue로 다시 띄워 턴을 이어 간다. 루프와 VM은 그대로 한 프로세스다. (c) 실행 분리: VM을 자식 프로세스에 두고 능력 호출, CL_AWAIT의 승인, 출력을 IPC로 부모(루프, 게이트, 세션 기록)와 주고받는다. 자식이 죽으면 부모가 그 run에 crashed 결과를 바로 채우고 새 VM으로 턴을 잇는다.
   - 대가: (b)는 대화형에서 터미널 상태(raw 모드)를 부모가 되돌려야 하고, 하네스 자신의 결함도 함께 덮는다. (c)는 능력 호출마다 IPC 왕복이 들고, 바인딩 층(VM 쪽)과 본체, 게이트(부모 쪽)가 프로세스로 갈리며, 취소 플래그와 벽시계 타이머가 프로세스를 건넌다. (b)와 (c) 모두 죽은 VM의 상태는 잃는다. 지금과 같다.
   - 판단 기준 (추천): E 회차에서 죽은 run이 run 1,000개당 1개를 넘거나, cyber에 요청해 고친 빌드로 다시 돌린 회차에서도 0이 아니면 (b)를 먼저 한다. (c)는 agentd가 한 프로세스에 여러 세션을 둘 때(아래 3) 다시 본다. 그때는 한 VM의 죽음이 다른 세션을 죽인다.
   - 추천: E의 측정 전까지 (a). 근거: 죽는 경로는 cyber에서 고친다(ADR 0019). 0.4.15 회차의 run 206개에서 죽은 run은 0이다. (b)는 (a) 위에 얹을 수 있어 나중에 더해도 버릴 것이 없다.
   - 정하는 때: ADR 0017 추천 10은 runtime 단계(M1), TODO는 M4에 두었다. 비율은 E에서 처음 나오므로 E 뒤에 정하는 것을 추천한다.

2. 터미널에 그리기 전 바이트 정리 (terminalSafe, ADR 0030 결정 8의 B3)
   - 요구: 하네스가 만들지 않은 바이트(모델의 글과 코드, 능력 출력, 파일 이름, 오류 문구)를 터미널에 그대로 쓰지 않는다. 제어 문자, DEL, 잘못된 UTF-8을 보이는 꼴로 바꾼다. 줄바꿈과 탭은 둔다. 이스케이프 시퀀스는 화면을 지우거나 커서를 옮겨 승인 프롬프트와 출력을 가릴 수 있다 (05 프롬프트 인젝션).
   - 자리: 프런트엔드다. 코어는 터미널을 모른다(위 경계 규칙). json과 stream-json은 JSON 문자열 이스케이프를 따른다.
   - 선택지: (a) 할당 없는 formatter와 조각 단위 증분판(조각 사이에서 나뉜 UTF-8 문자를 이어 받는다). fx의 B3이 약 150줄이다. (b) 그리기 전에 문자열 전체를 한 번에 바꾼다(할당). (c) 하지 않는다.
   - 추천: (a)를 대화형과 헤드리스 text 모두에, stdout이 터미널이든 파이프든 같게. 근거: 모델 출력은 스트림 조각으로 오고 UTF-8 문자가 조각 사이에서 나뉜다 (10 스트림 풀기). 할당이 없으면 그리는 길에 실패 경로가 없다. 출력이 터미널 여부에 따라 달라지지 않아 테스트가 같은 바이트를 본다.

3. agentd에서 여러 세션을 어떻게 나눌지 (fiber 안 await의 양보, TODO M6)
   - 사실: fiber 안에서 호스트 Future를 await하면 그 fiber만 멈추고 eval은 나가지 않는다 (08). 이것은 한 VM 안의 전환이다. eval은 끝나거나 CL_AWAIT, 상한, 인터럽트로만 스레드를 놓는다. 한 스레드에서 여러 VM의 eval을 번갈아 돌리는 것은 확인하지 않았다.
   - 선택지: (a) 세션마다 프로세스. agentd는 tars-agent 프로세스들을 stream-json으로 잇는 프런트엔드다 (ADR 0004). (b) 한 프로세스, 세션마다 스레드. (c) 한 스레드에 여러 VM을 두고 CL_AWAIT와 eval 경계에서 바꿔 돈다.
   - fiber 안 await의 양보가 쓰일 자리는 한 세션의 스크립트가 여러 능력 호출을 동시에 기다릴 때다. 세션 사이의 전환에는 직접 쓰이지 않는다. v1의 안내는 fiber를 가르치지 않는다 (ADR 0016).
   - 추천: (a). 근거: 프로세스 격리가 "다른 세션이 막히지 않는다"와 VM 크래시 격리(위 1)를 함께 준다. VM 하나가 약 2.6 MiB라 프로세스 수의 부담이 작다. (c)는 계산 루프를 도는 스크립트 하나가 연료나 벽시계 상한까지 스레드를 쥐고, 한 VM이 죽으면 모든 세션이 죽는다.
   - 정하는 때: agentd를 설계할 때 (M6, ADR 0029의 AHP 검토와 함께).

4. 비기능 예산: 메모리, 시작 시간, 실행 파일 크기 (ADR 0030 결정 8의 B6)
   - 실측: VM 하나가 쥔 메모리 약 2.6 MiB, VM 생성과 첫 eval 개당 2~3 ms, 같은 VM의 validate와 eval 200회에 각 1~2 ms (08, macOS arm64). libcyber.a는 arm64 3.06 MB, x86_64 3.62 MB다(정적 라이브러리 전체다. 실행 파일에 링크되는 몫은 이보다 작을 수 있다). spike/s2 실행 파일(provider, VM, 능력 셋, macOS arm64, 2026-11-18 빌드)은 3,416,672바이트다. s2의 호스트 쪽 최적화 모드는 확인하지 않았다. 하네스 프로세스 전체의 메모리와 시작 시간은 재지 않았다. 09의 지시서 목표는 유휴 5 MB 이하이고 VM 하나는 이 안에 든다. ADR 0004의 "첫 VM 약 7 MB"는 측정 조건을 확인하지 않았다.
   - 후보 (추천):
     - 유휴 메모리: 세션을 열고 입력을 기다릴 때 RSS 16 MiB 이하. 실행 중 최대는 유휴 값에 VM 메모리 상한(256 MiB, 05)을 더한 것이다. 근거: VM 2.6 MiB에 실행 파일 매핑, TLS와 HTTP 버퍼, 히스토리가 더해진다. 패널 여덟에 하나씩 띄우면(ADR 0004) 유휴 128 MiB다.
     - 시작 시간: `tars-agent --version` 10 ms 이하, 새 세션을 열어 첫 요청을 보내기 직전까지 100 ms 이하(네트워크 제외, macOS arm64 개발 기계). 근거: VM과 머리말 eval이 수 ms이고 나머지는 설정, AGENTS.md(40,000자 이하), git 저장소 확인이다. tars 게스트(QEMU)는 따로 재서 적는다.
     - 실행 파일 크기: x86_64-linux-gnu 릴리스 산출물 8 MiB 이하. 커밋 사이에 256 KiB 넘게 커지면 경고한다. 근거: libcyber.a 전체(3.62 MB)와 s2(3.4 MB)를 더해도 이 안이다. 산출물은 tars ISO의 devlayer에 들어간다 (ADR 0005).
   - CI의 처리 (추천): 크기와 시작 시간은 넘으면 실패, 메모리는 기록만 한다. 근거: 메모리는 히스토리 길이에 따라 흔들린다.
   - 같이 정할 것: 릴리스 빌드의 최적화 모드(ReleaseSafe 또는 ReleaseFast)와 strip. 크기와 안전 검사가 여기에 달렸고 명세에 없다.
