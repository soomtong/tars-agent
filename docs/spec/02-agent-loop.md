# 에이전트 루프

## 메시지와 히스토리

- 코어는 자체 메시지 모델만 본다 (10, ADR 0015). 역할은 user, assistant이고 메시지 하나가 블록의 목록이다. assistant 블록은 thinking, text, tool_call(CodeAct에서는 이름 run, 인자 { code })이다. user 블록은 text, tool_result(tool_call의 id, content, is_error)이다.
- 시스템 프롬프트는 히스토리 밖에 따로 둔다. 어댑터가 형식에 맞는 자리에 싣는다 (10).
- 히스토리는 덧붙이기만 한다. 이미 보낸 메시지를 고치거나 지우지 않는다. 사고 블록은 그것을 만든 대화 안에서만 유효하고, 앞부분을 고치면 프롬프트 캐시도 깨진다. 줄여야 할 때는 컴팩션으로 새 히스토리를 시작한다.
- assistant 응답은 사고 블록을 포함해 받은 그대로 보관하고 그대로 되돌려 보낸다. 형식마다 다른 원문(Anthropic 형식의 서명)은 thinking 블록의 불투명 칸에 출처 형식과 함께 들고, 같은 형식으로 보낼 때 그 형식의 어댑터만 되살린다. 세션 중간에 형식이 바뀌면 다른 형식의 원문은 버린다. 글과 도구 호출은 남고 사고는 빠진다 (10).

## 모델 요청

- 전송 형식은 둘이다: Anthropic Messages, OpenAI Chat Completions. 제공자는 설정 데이터이고 형식별 요청의 모양은 어댑터가 정한다 (10, ADR 0014, 0015).
- 개발 기본 제공자는 DeepSeek이다. 평가 모델 목록과 판정의 기본 모델은 13에 있다. 제공자 항목은 내장 기본 항목에 settings.json이 더하거나 덮는다 (10 "제공자 설정"). 모델은 설정 키 model로 바꾼다 (11).
- 스트리밍만 쓴다.
- max_tokens, effort, 캐시 지점은 힌트 옵션이다. 지원하는 어댑터는 쓰고 못 하는 어댑터는 무시한다 (10). 기본값은 max_tokens 4096이고 effort는 보내지 않는다. temperature와 응답 프리필은 쓰지 않는다.
- tool_choice는 auto다. 강제 도구 선택은 쓰지 않고 "행동은 run으로만 한다"를 시스템 프롬프트로 지시한다.
- run 도구의 스키마는 { code: string }이다. 인자 조각을 스트림으로 받아 코드가 써지는 대로 화면에 보인다. 입력 JSON은 하네스가 직접 검증한다.
- 캐시: 시스템 프롬프트는 세션 동안 바이트 단위로 고정한다. 시각, 작업 상태처럼 변하는 값은 시스템 프롬프트에 넣지 않는다. 앞부분이 그대로여야 제공자의 캐시가 맞는다. 캐시 지점을 표시하는 형식에서는 어댑터가 표시를 둔다 (10).
- 세션 중 바뀌는 지시(모드 변경, 할 일 알림)는 시스템 프롬프트를 고치지 않고 하네스 알림으로 히스토리에 덧붙인다. 캐시된 앞부분이 유지된다. 하네스 알림은 다음에 보내는 user 메시지에 `<harness-notice>` 표시를 붙인 text 블록으로 든다. 두 형식이 같은 모양이다 (10 "하네스 알림").
- 프로젝트 지시 파일(AGENTS.md)은 첫 user 메시지 앞에 붙인다. 시스템 프롬프트는 모든 프로젝트에서 같게 유지된다.

## 한 스텝의 절차

1. 요청을 보내고 스트림을 받는다. text와 코드를 프런트엔드에 흘린다.
2. 끝난 이유를 먼저 본다. 제공자가 준 값이 아니라 어댑터가 응답 내용에서 다시 계산한 값이다 (10 "끝난 이유").
   - end_turn: 턴을 끝낸다.
   - tool_use: 3으로 간다. 한 응답에 run 블록이 여럿이면 순서대로 실행하고 결과를 user 메시지 하나에 모두 담는다.
   - max_tokens: 잘린 코드는 실행하지 않는다. 잘렸다는 오류 결과를 돌려주고 더 작은 단위로 쓰라고 알린다.
   - refusal: 실행하지 않는다. 사용자에게 거절 범주를 보이고 턴을 끝낸다. 서버 쪽 fallbacks 옵션을 쓸지는 10 열린 것 1이다.
   - pause_turn: 그대로 이어서 요청한다.
   - other: 모르는 끝난 이유다. 턴을 끝내고 제공자가 준 원값을 사용자에게 보인다.
3. 검증: cl_vm_validate로 세션 VM 위에서 컴파일만 한다. 실패하면 컴파일 오류를 is_error 결과로 돌려주고 실행하지 않는다. 오류는 cl_vm_compile_error로 구조화해 받는다(종류, 메시지, 줄, 열, 표시 길이. 줄과 열은 0부터라 1을 더해 보인다). 모델에게는 요약 문자열(cl_vm_compile_error_summary, 이스케이프 코드 없음)을 주고 세션 기록에는 구조화한 필드를 남긴다. 컴파일러는 첫 오류에서 멈추므로 한 번에 오류 하나다. 오류 모아 받기(cl_vm_set_error_recovery)와 검증 뒤의 cl_vm_symbol_hints는 켜지 않는다. 켤지는 아래 열린 것 1이다.
4. 실행: 연료(fuel), 벽시계(wall-clock) 타이머, 스택 상한, 메모리 상한을 걸고 cl_vm_evalx로 실행한다. 벽시계는 스크립트가 VM 안에서 보낸 시간만 잰다. 바인딩 층이 능력 본체를 부르기 전에 타이머를 멈추고 돌아온 뒤 다시 시작한다. 능력 안의 시간은 능력 자신의 시간 제한(proc.exec의 timeout_ms 등)과 취소 플래그가 맡는다 (03, ADR 0021). CL_AWAIT로 돌아오면 타이머를 멈추고 승인을 받아 Future를 완료한 뒤 cl_vm_resume으로 이어 간다. 거부는 error.Denied로 완료, 취소는 resume하지 않고 cl_vm_abandon으로 버린다. 멈춘 동안 들어온 interrupt 요청은 resume이 지우므로 타이머가 울려도 무해하다. 타이머는 resume 직전에 다시 시작한다. 기다리는 Future의 요청은 cl_future_tag로 찾는다. 스크립트가 능력 호출을 fiber나 scope 블록에 넣어 요청이 여럿 걸리면 cl_vm_pending_futures의 목록에서 요청 번호가 가장 작은 것 하나만 묻고 완료한 뒤 resume하며, 남은 것은 다음 CL_AWAIT에서 목록을 다시 읽어 처리한다 (ADR 0016). 묻지 않은 채 버려진 요청은 eval이 끝날 때 요청 표를 비우며 사라진다. 목록에 우리 요청이 없으면(태그가 모두 0, 능력이 만든 것이 아니면) 버리고 interrupted로 돌려준다 (ADR 0011). persist_main으로 함수, 타입, use 선언, main 지역 변수가 다음 eval로 이어진다.
5. 결과 조립: printer 콜백으로 모은 출력, 마지막 표현식 값(res, res_t, cl_value_desc), 오류. 상한을 넘으면 03의 넘침 규칙을 따른다. 실패한 결과도 그때까지의 출력을 남기고, 끝에 이번 스크립트가 부른 능력의 목록(이름과 상태 ok, error, denied, cancelled)을 붙인다. 실패 전에 일어난 부작용은 되돌리지 않으므로 모델이 무엇이 이미 일어났는지 알아야 한다.
6. tool_result를 담은 user 메시지를 만든다. 기다리는 하네스 알림이 있으면 tool_result 블록들 뒤에 붙인다 (10 "하네스 알림"). steering 큐에 입력이 있으면 하나를 꺼내 같은 메시지의 맨 뒤에 text 블록으로 붙인다 (아래 "실행 중 입력"). 히스토리에 덧붙이고 1로 돌아간다.

기록 순서: 코드는 실행 전에, 능력 호출은 호출마다, 결과는 실행 뒤에 세션 파일에 쓴다. 프로세스가 죽어도 무엇을 하다 죽었는지 남는다.

## 실패는 모두 결과

루프는 스크립트 때문에 죽지 않는다. 실패는 종류마다 구분되는 문구로 돌아간다.

| 종류 | 원인 | VM 상태 |
|---|---|---|
| compile error | validate 실패 | 유지 |
| panic | CL_ERROR_PANIC. 스택 오버플로와 OutOfMemory 포함. 트레이스는 양 끝 20프레임 | 최상위 변수 초기화, 함수와 use는 유지 |
| interrupted | 연료 소진, 벽시계 초과, 사용자 인터럽트 | 최상위 변수 초기화, 함수와 use는 유지 |
| denied | 사용자가 승인을 거부 | 유지 (오류 값으로 돌아간다) |
| capability error | 스크립트가 처리하지 않은 능력 오류 값이 main 밖으로 나감. 처리한 오류는 ok이고 능력 목록에 error로 남는다 (06) | 유지 |
| crashed | 실행 중 프로세스가 끝남. 재개할 때 채운다 | 새 VM |

- 최상위 변수가 초기화된 경우 결과 끝에 그 사실을 붙인다(top-level variables were reset). 함수와 타입 선언, use는 남는다. 남겨야 할 값은 memo 능력에 둔다.
- VM의 첫 컴파일 실패, 컴파일러나 지역 이월 중의 할당 실패 뒤에는 다음 eval이나 검증이 reset된 VM에서 시작한다. 루프는 CL_SUCCESS가 아닌 eval과 검증 뒤에 cl_vm_reset_pending을 묻고, true면 머리말을 다시 돌리고 결과에 세션이 reset됐다고 적는다. 보통의 컴파일 오류 뒤에는 세션이 그대로다.
- 빈 출력은 ok와 실행 요약(능력 호출 수, 걸린 시간)으로 채운다.

## 제공자 오류

응답이 어느 종류인지는 어댑터가 가른다 (10 "오류와 재시도"). 처리는 형식과 무관하다.

- 재시도할 오류(429, 5xx와 Anthropic의 529, 연결 끊김, 스트림 중간 끊김): 지수 백오프로 재시도한다 (기본 5회, retry-after 존중). 상한을 넘으면 오류로 턴을 끝낸다. 무한히 재시도하지 않는다 (ADR 0030). 스트림 중간에 끊기면 그 응답을 버리고 같은 요청을 다시 보낸다.
- 요청 오류(400, 401, 403, 404): 재시도하지 않고 사용자에게 보인다. 401과 403에는 어느 key_env를 썼는지 함께 보인다. 히스토리는 요청 전 상태로 둔다.
- 컨텍스트 초과: 요청 오류 가운데 어댑터가 오류 본문으로 가른 것이다. 컴팩션을 한 번 하고 다시 보낸다.
- 오류와 재시도는 세션 파일에 error 줄로 남는다 (07).

## 한도

- 턴당 스텝 수 (기본 50), 스텝당 연료, 스텝당 벽시계 (기본 120초, 능력 안의 시간은 빼고 잰다), 세션 토큰 예산 (선택)
- 같은 코드가 3회 연속 같은 오류로 실패하면 결과에 경고를 붙이고, 5회면 턴을 끝내고 사용자에게 넘긴다. crashed도 오류로 센다.
- 헤드리스는 --max-steps, --max-budget-usd를 받는다.

## 인터럽트

- Esc 또는 Ctrl-C 한 번: 스트림을 받는 중이면 요청을 끊고, 스크립트 실행 중이면 cl_vm_interrupt를 부르고 취소 플래그를 세운다.
- cl_vm_interrupt는 능력 함수 안에서 막힌 호출을 못 끊는다. 막힐 수 있는 능력(프로세스 대기, HTTP)은 취소 플래그를 스스로 확인하고 돌아온다 (03). 승인 대기는 VM 밖이라 해당하지 않는다 (ADR 0011).
- 끊긴 턴도 히스토리에 남는다. 실행하지 못한 tool_call에는 interrupted 결과를 채워 메시지 짝을 맞춘다.

## 실행 중 입력 (steering, ADR 0021)

- 모델이 응답하거나 스크립트가 도는 동안 사용자가 입력을 마치면(Enter) 코어의 steering 큐에 들어간다. 스크립트를 끊지 않는다. 끊으려면 인터럽트를 쓴다.
- 루프는 스텝마다 큐에서 하나만 꺼내 tool_result와 같은 user 메시지에 text 블록으로 붙인다. 역할이 user, assistant로 번갈아 이어진다. 한 번에 하나씩 넣어 모델이 입력마다 응답할 기회를 준다.
- 세션 파일에는 붙인 시점에 user 줄로 쓴다 (07).
- 턴이 끝날 때 큐에 남은 입력은 다음 턴의 입력이 된다. 하나씩 차례로 턴을 연다.
- 인터럽트로 턴을 끊으면 큐에 남은 입력은 프런트엔드의 입력 줄로 돌려준다. 사용자가 고치거나 지우고 다시 보낸다.
- 프런트엔드에 보이는 큐의 상태(대기 수, 내용)는 코어가 이벤트로 낸다.

## 컴팩션

- 입력 토큰이 임계치(컨텍스트 창의 80%)를 넘거나 사용자가 /compact를 치면 한다.
- 방식: 모델에게 지금까지의 요약을 쓰게 하고, 그 요약을 첫 user 메시지로 하는 새 히스토리를 시작한다. 옛 히스토리는 세션 파일에 남고 요청에서만 빠진다. 히스토리 중간을 고치는 방식은 쓰지 않는다.
- 요약 요청: 대화를 대화로 보내지 않고 `[User]:`, `[Assistant]:`, `[Code]:`, `[Result]:` 표시를 붙인 텍스트로 풀어 user 메시지 하나에 담는다. 모델이 요약 대신 대화를 이어 쓰지 않게 하기 위해서다. 사고 블록은 넣지 않는다. 결과는 2,000자에서 자르고 자른 글자 수를 적는다. 요약 요청에는 캐시 지점을 두지 않는다 (다시 쓰이지 않는다).
- 요약의 틀 (영어 머리말, 모델이 채운다):

~~~text
## Goal                    사용자가 이루려는 것
## Constraints & Preferences  사용자가 말한 요구와 이후 지시
## Progress
### Done / ### In Progress / ### Blocked
## Key Decisions           결정과 이유
## Next Steps              다음에 할 일, 순서대로
## Critical Context        이어서 일하는 데 필요한 값, 경로, 오류 문구
~~~

- 호스트가 요약 뒤에 덧붙이는 것: 읽은 파일과 고친 파일의 목록(세션의 파일 상태와 cap 줄에서 누적한다. 이전 요약의 목록도 이어받는다), 할 일 목록, memo 키 목록, VM에 살아 있는 함수와 변수 이름.
- 두 번째 컴팩션부터는 이전 요약을 주고, 그 뒤의 대화를 반영해 요약을 고치게 한다. 처음부터 다시 쓰지 않는다.
- 최근 구간을 원문으로 남기지 않는다. 새 히스토리는 요약 하나로 시작한다. 남길지는 아래 열린 것 2다.
- VM은 컴팩션과 무관하게 살아 있다.

## 세션 재개 (ADR 0008)

- --continue (이 디렉터리의 마지막 세션), --resume <id>.
- 히스토리는 세션 파일에서 복원한다. VM 상태는 복원하지 않는다. 과거 코드를 다시 실행하면 부작용도 다시 일어나기 때문이다.
- 재개한 뒤 처음 보내는 user 메시지에 "VM이 새로 시작됐다. 이전에 정의한 함수와 변수는 없다"는 하네스 알림을 넣는다. memo 값과 할 일 목록은 세션 파일에서 복원한다.
- 크래시 뒤 재개 (ADR 0021): 세션 파일이 결과 없는 run 줄로 끝나면 그 tool_call에 crashed 결과를 채워 짝을 맞추고 result 줄로 기록한다. 결과에는 "이 스크립트를 실행하던 중 프로세스가 끝났다"와, 그 run 뒤에 기록된 cap 줄의 능력 호출(이미 효과가 났을 수 있다)을 적는다. 응답 하나에 run 블록이 여럿이었으면 실행하지 못한 나머지에는 interrupted 결과를 채운다. 스크립트는 다시 실행하지 않는다. 사용자에게도 같은 내용을 보이고, 그 스크립트가 crash/에 보관됐음을 알린다.

## 열린 것

구조에 닿으므로 사용자가 정한다 (ADR 0012). 추천은 Claude의 것이다.

1. 검증 오류를 여럿 돌려줄지, 검증 뒤 힌트를 넘길지 (검토 문서 9절 13, 18, TODO E)
   - 사실 (08, 검토 3.5): cl_vm_set_error_recovery를 켜면 구문 오류는 전부, 구문 오류가 없으면 본문(main 블록, 함수, 메서드)마다 첫 오류 하나가 오고, 선언 오류가 섞이면 하나에서 끝난다. cl_vm_compile_report가 그 전부를 준다. 실패한 검증 뒤에도 세션이 남는다. cl_vm_set_symbol_info를 켜고 검증하면 cl_vm_symbol_hints가 쓰지 않는 지역과 use, 추론 타입을 준다. 세션의 최상위 지역도 unused로 나오므로 호스트가 거른다. 실패한 검증 뒤에는 unused를 내지 않는다.
   - 선택지 (오류): (a) 끈다. 한 번에 오류 하나(지금 본문). (b) 켜고 오류 전부를 결과 하나에 담는다.
   - 선택지 (힌트): (a) 넘기지 않는다. (b) 검증을 통과한 스크립트의 쓰지 않는 함수 안 지역을 결과 끝에 경고로 붙인다. 실행은 그대로 한다.
   - 추천: 둘 다 (a)로 M1을 시작하고, E에서 켠 회차와 끈 회차를 같은 과제로 비교해 정한다. 비교 값은 과제당 스텝 수, 입력 토큰, 과제 성공률이다. 판정 지표인 첫 시도 validate 통과율(13)은 오류 문구를 보기 전의 코드라 이 선택에 움직이지 않는다. 근거: 모델은 한 스텝에 오류 하나씩 고쳤다(검토 5절). 오류를 모아 주면 스텝이 줄 수 있고, 경고는 스텝과 토큰을 더 쓰게 할 수도 있다.
   - 확인하지 않은 것: 오류가 여럿일 때 요약 문자열(cl_vm_compile_error_summary)이 무엇을 담는지. 문맥(이전 선언, 템플릿 호출 지점)은 요약에만 있다 (08). (b)를 고르면 세션 run 줄의 validate 결과에 오류 여럿을 담는 모양을 07에서 정한다.

2. 컴팩션에서 최근 구간을 원문으로 남길지 (ADR 0021 열어 둔 것, ADR 0030 결정 8의 A6, TODO M4)
   - 선택지: (a) 요약만(지금 본문). (b) 최근 구간(pi는 약 20k 토큰)을 원문으로 두고 user 메시지 경계에서 자른다. 그 앞만 요약한다. (c) fx식: 접힌 구간에서도 user 메시지와 턴의 최종 답은 글자 그대로 두고, 최근 턴 최대 넷을 원문으로, 사이의 일만 요약한다.
   - 막는 것: 원문 구간의 assistant 블록은 사고 블록과 tool_call을 담는다. 앞부분이 바뀐 대화(요약 뒤)에 남긴 사고 블록을 제공자가 받는지 확인하지 않았다 (10 확인하지 않은 것). 사고 블록만 빼고 보내면 받는지도 확인하지 않았다. VM은 컴팩션과 무관하게 살아 있으므로 원문 구간의 실행 결과와 VM 상태는 어긋나지 않는다.
   - 추천: (a)로 M4를 시작한다. M4의 확인(두 형식, DeepSeek과 OpenRouter)에서 사고 블록을 받으면 (b)로 간다. 근거: (a)는 확인할 것이 없고 덧붙이기만(ADR 0008)과 맞는다. (b)는 직전 작업의 맥락이 요약에서 덜 빠지고, user 메시지 경계에서 자르므로 tool_call과 tool_result의 짝이 깨지지 않는다. (c)는 user 메시지를 모두 남겨 긴 세션에서 줄이는 양이 사용자 입력의 크기에 묶인다.
   - 같이 정할 것: 원문 구간의 크기(토큰 수 또는 턴 수), 원문 구간만으로 임계치(80%)에 가까울 때의 처리.

3. 검증 중에 프로세스가 죽은 run의 짝 맞추기 (01 "프로세스가 죽을 때의 대응"의 빈 곳)
   - 사실: run 줄은 검증 결과를 담아 검증 뒤에 쓴다 (07). 검증 중에 죽으면 세션 파일은 tool_call을 담은 assistant 줄로 끝나고 run 줄이 없다. 위 "세션 재개"는 결과 없는 run 줄만 본다. 짝이 맞지 않는 히스토리는 제공자가 거부한다 (ADR 0021 근거 1).
   - 선택지: (a) 재개가 결과 없는 tool_call(뒤에 run 줄이 없는 것)에도 crashed 결과를 채우고, 코드를 assistant 줄에서 꺼내 crash/에 보관한다. 07의 줄 모양은 그대로다. (b) run 줄을 검증 전에 쓰고 검증 결과는 따로 적는다. 07의 run 줄 모양이 바뀐다.
   - 추천: (a). 근거: 코드는 이미 assistant 줄에 있다. 줄 모양을 바꾸지 않고 재개 규칙 한 줄로 막는다. 전제는 assistant 줄을 검증 전에 쓰는 것이다. 지금 02와 07은 assistant 줄을 쓰는 때를 적지 않는다.
